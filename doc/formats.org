#+TITLE: Formats

The byte-level formats poslib and [[https://github.com/ClankaOperatingSystem/pyposlib][pyposlib]] share. Both implement
this document, version 20, in lockstep; the fixtures in =fixtures/= are its
examples, and both test suites run all of them. Org interpretation is not
shared: it has one implementation, poslib's.

* Content identifiers

A file's or directory's CID is the one =ipfs add= computes under the
unixfs-v1-2025 import profile of [[https://specs.ipfs.tech/ipips/ipip-0499/][IPIP-499]]:

- CIDv1, sha2-256, written in multibase base32, lower case (=b...=).
- A file is cut into 1 MiB chunks, each a raw block. One chunk, including
  an empty file, is its own CID. More chunks form a balanced DAG of dag-pb
  UnixFS file nodes of at most 1024 links, levels built from the left.
- A directory is a dag-pb UnixFS directory node linking its entries in
  byte order of their names; each link's size is the whole DAG beneath it.
- Names are hashed as stored, in whatever Unicode normalisation.
- Hidden entries, those whose names begin with =.=, are left out.
- Symlinks and other special files are refused.
- A directory node of more than 262144 bytes, which IPFS would shard, is
  refused (=sharding-unsupported=) until sharding is implemented.

Fixtures: =fixtures/cid/=. Each gives a tree, the entry to hash, and its
CID or error. =params= overrides the chunk size and link limit, as
=--chunker= and =--max-file-links= do. kubo, run offline, is the referee.

** From an inventory

The CID of every directory in a tree, its root included, follows from
its files' paths, CIDs and sizes alone, with no bytes read. A file's DAG
size is a function of its size under the profile, since a leaf's is its
chunk's, a node's is its block's plus its children's, and a binary CID is
36 bytes whatever it hashes; and a directory's block is its links, each a
child's CID, name and DAG size, in byte order of name. So a ledger's
enrolled entries give the archive's root, and a reader with the ledger
and not the archive computes the CIDs a reader with the archive does.

A directory that holds nothing has no file to derive it from, and IPFS
hashes it all the same. So an inventory lists its empty directories
beside its files, by path, and with them gives every CID the tree on
disk has. A directory holding only hidden entries is empty, since IPFS
leaves those out; an inventory holding a hidden component is refused.

Fixtures: =fixtures/inventory/=. Each gives a tree, the entry to hash,
and =cids=, the CID of every file and directory under it, the root as
=.=; =params= as for =fixtures/cid/=. The tree on disk and the inventory
of its files must both give them, and kubo, run offline, is the referee
for the root.

* DAG-JSON

Ledger events, checkpoints, plans and reports are [[https://ipld.io/specs/codecs/dag-json/spec/][DAG-JSON]], IPLD's JSON
written one way, so that equal values are equal bytes, kept to the
values a ledger needs:

- Values: objects, arrays, strings, integers of 64 bits and =null=; no
  floats and no booleans.
- Object keys in the byte order of their UTF-8 encoding, which is code
  point order, each once.
- No whitespace between tokens.
- Strings in UTF-8, unescaped, except: =\"= and =\\=; =\b=, =\f=, =\n=,
  =\r= and =\t=; other characters below U+0020 as =\u00xx=, lower-case
  hex. DEL and all non-ASCII characters are written raw.
- Integers in decimal, without sign unless negative, without exponent.
- A link to a block is the object ={"/": "CID"}=, and the key =/= is in
  no other object.

A value written so is a block, and the block's CID is CIDv1 with the
dag-json codec (=0x0129=) and sha2-256 over its bytes, in base32
(=baguqeera...=): what =ipfs dag put --input-codec dag-json --store-codec
dag-json= stores and names. A schema 3 event is a block. Canonical JSON,
which schema 1 and 2 events, checkpoints, plans and reports are written
in, is the same bytes and one newline after them, so a canonical JSON
event less its newline is a block too.

A block is read strictly: bytes that are not the one encoding of their
value are refused (=encoding=).

Fixtures: =fixtures/json/=, each a value and its canonical JSON;
=fixtures/dag-json/=, each a value, its block and the block's CID, or
bytes that are not a block, refused. kubo, run offline, is the referee
for those blocks and for every schema 3 event in =fixtures/ledger/=.

* Archive ledgers

Each outermost =archives/= directory has a ledger. A scope keeps its
ledger and checkpoints beside its archive, in =archive-integrity/=:

- =archive-integrity/ledger/=: the ledger's events;
- =archive-integrity/checkpoints/=: checkpoints of ledger heads.

The archive itself then holds only archived material. When a scope
retires into its parent's archive, its =archive-integrity/= goes with it,
as ordinary content inside the parent's CID.

The legacy layout, read until archives are migrated, keeps the ledger
inside the archive, in =archives/.archive-integrity/=, and checkpoints in
=.archive-integrity-anchors/= beside the root. An archive with a ledger in
both places is refused (=ledger=).

** Kept archives

A scope's archive is on disk, beside its ledger, or kept by a keeper, a
server that holds its bytes (=doc/remote-archive-protocol.txt=). The
scope's node says which, in its configuration
(=doc/pos-directory.txt=). The node is the nearest directory at or
above the scope that holds a configuration, and the scope's entry under
=archives= is the one whose =scope= is its path from there, =.= for the
node itself. An entry kept =remote= gives the keeper's =url=. A scope with
no entry, or beneath no node, keeps its archive on disk, as does one kept
=committed= or =uncommitted=. A configuration that document refuses is
refused (=config=), as are two configurations in one node.

An archive a keeper keeps has its ledger with its scope, as any other,
and no file in =archives/=, which need not exist. One that holds a file
is refused (=kept=): it has not been moved to its keeper ([[*Keeping][Keeping]]). What it holds
is what its ledger enrols, and its CIDs are those the ledger folds to
([[*From an inventory][From an inventory]]), so its ledger enrols a CID for every entry, else
=entry=. Discovery and planning read a kept archive from its ledger alone
and ask its keeper nothing. The check reads it from its ledger and then
asks its keeper what it holds ([[*Check][Check]]). Applying a plan sends the
seal to the keeper ([[*To a keeper][To a keeper]]).

A scope's entry may also name its ledger, by =ledger=, with an archive
kept any way. A keeper may be bound to a ledger's id before the ledger
has an event, so the entry says what the id is: a ledger's first event
takes it ([[*Plans][Plans]]). A ledger with events that is not the one named, its
last =ledger_id= another or none, is refused (=identity=) by the check
and by planning.

** Discovery

From a root: the root itself if it is named =archives=; otherwise every
directory named =archives= beneath it, not descending into one found, nor
into any directory whose name begins with =.= or =_=. A symlinked
directory met on the way is refused.

An archive a keeper keeps is found by its ledger: for each directory met
on that walk, the root included, that holds =archive-integrity/ledger/=
and no =archives=, its =archives= is found if a keeper keeps it. A root
named =archives= that does not exist is such an archive, or is refused
(=root=).

** Inventory

Every file beneath the archive, except a legacy ledger directory at its
top, hidden and underscored files included. Each is a regular file with
one link, else refused; a symlinked directory is refused. Each entry is:

- =sha256=: lower-case hex of its bytes;
- =size=: its length;
- =mode=: its permission bits, the low twelve, with every write bit
  cleared.

Paths are relative, =/=-separated, with no empty, =.= or =..= component.
An archive not yet made has an empty inventory.

** Collections

A collection is a directory whose =README.org= contains the line
=#+COLLECTION: t=: those exact bytes, between line feeds or the file's
ends; or a capsule, a directory whose =manifest.json= is an object with
=schema_version= 1, =entries= and =entrypoint=. The event that seals it
lists its path. A capsule is a frozen snapshot with its own verification,
kept byte for byte: its links are left as written, broken ones included,
and no =README.org= is added to it.

** Events

The ledger is a sequence of files named =NNNNNNNN-NAME.json=: an
eight-digit number counting from 1 without gaps, and what names the
event. A schema 1 or 2 event is canonical JSON, named by the SHA-256 of
the file's bytes; a schema 3 event is a block, named by its CID. Once an
event has schema 2, every later one has schema 2 or 3; once one has
schema 3, every later one does.

Schema 1:

- =schema=: 1.
- =previous=: the hash of the preceding event, =null= for the first.
- =add=: the entries enrolled, by path. A path is enrolled once; no path
  lies in a legacy ledger directory; no mode has a write bit.
- =ledger_id=: a UUID in canonical lower-case form, the same in every event
  that has one. Once present it stays; events before the first that has
  one may lack it.

Schema 2 has the same, with =ledger_id= required, and:

- each entry in =add= also has =cid=, the file's CID;
- =item=: the path of the item the event sealed, a file or a directory;
  every path in =add= and =collections= is the item or lies within it;
- =root=: the archive's CID after this event;
- =collections=: the paths of the collections this event seals, sorted,
  each once; possibly none.

A conversion event, once in a ledger that holds legacy entries (those
without =cid=), migrates them all: =schema= 2, =kind= =conversion=,
=previous=, =ledger_id=, and:

- =remove=: legacy paths no longer enrolled, sorted;
- =rename=: each legacy path renamed, by its old path, to its new;
- =convert=: every legacy entry left, by its path after renaming, as a
  schema 2 entry with =from=, the SHA-256 it was enrolled with;
- =add=: files enrolled for the first time, as schema 2 entries;
- =collections=: every collection in the archive, sorted;
- =root=: the archive's CID after it.

Schema 3 has what schema 2 has, as a block, and:

- =previous=: a link to the preceding event's block, =null= for the
  first;
- =empty=: the paths of the empty directories in the item, sorted, each
  once, possibly none; a directory holding only hidden entries is one,
  since IPFS adds the directory and leaves those out;
- =root=: the CID the ledger folds to after this event: that of the
  inventory of its enrolled entries, less hidden ones, and its enrolled
  empty directories ([[*From an inventory][From an inventory]]). It is the archive's CID
  whenever the archive holds what its ledger enrols and nothing else.

A ledger's first event may be of schema 3. A ledger of schema 2 that
holds no legacy entry is brought to schema 3 by one event: =schema= 3,
=kind= =conversion=, =ledger_id=, and:

- =previous=: a link to the block the preceding event is, less its
  newline;
- =from=: the SHA-256 the preceding event is named by;
- =empty=: every empty directory in the archive, sorted;
- =root=: the CID the ledger folds to, the root the preceding event
  recorded.

The head is what names the last event, its hash or its CID; the recorded
root is the last event's =root=, if it is of schema 2 or 3. An empty
ledger directory is refused. Refusals are named: =ledger= (the ledger is
not a directory, or there are two), =sequence= (name, number, hash or
CID), =encoding= (a schema 3 event that is not a block), =chain= (keys,
schema or =previous=, an event named otherwise than its schema is, a
conversion where there is nothing to convert, or one whose =from= is not
the head), =identity=, =entry= (an entry, =item=, =root=, =collections=
or =empty=, or a conversion that leaves a legacy entry unaccounted for,
names a wrong original or adds over an entry) and =empty=; =link=
refuses a symlink or a second hard link anywhere.

** Checkpoints

A checkpoint records ledger heads, to detect a vanished archive or a
truncated ledger. It lives in =archive-integrity/checkpoints/= beside the
root it covers, or in the legacy =.archive-integrity-anchors/=, named by
the SHA-256 of its bytes, holding in canonical JSON:

- =schema=: 1;
- =heads=: sorted heads, each an event's hash or its CID;
- =coverage=: =archive= for a root named =archives=, else =tree=.

Every head a checkpoint names must name some event file of the archives
found, or of a ledger within them, legacy or current, as retired scopes
carry, by its hash or by its CID as a block; otherwise the check refuses
(=anchor=). A ledger within an archive a keeper keeps is known by the
names its events are enrolled under.

Checkpointing a root records the distinct heads of the archives found
under it, once the check reports nothing changed, missing, new or
writable (else =unclean=). A new checkpoint goes to
=archive-integrity/checkpoints/= beside the root if =archive-integrity/=
exists there, else to the legacy folder. A checkpoint of the same bytes
already there is kept; a different one under the same name refuses
(=checkpoint=).

Repairing a root removes write bits from the enrolled files, ledger
events and checkpoints under it, and from nothing else; it enrols
nothing. It restores recorded read permissions when content matches,
but refuses changed bytes, changed executable or special mode bits,
and missing files (=differs=). Before changing anything, repair validates every archive
and the paths of its recorded empty directories. Before restoring any
directory, the schema 3 ledger's enrolled files and empty directories
must reconstruct the recorded root, else =root=. Missing directories are recreated, including
their missing parents; a file or symlink in the way refuses (=differs=,
or =link= when inventory detects the symlink). No ledger or checkpoint
bytes change, and no unrecorded directory is invented or removed.

The result gives =repaired=, the files whose permissions were repaired;
=restored=, the directories created; and =unregistered=, the unknown
files left alone. Run =repair= after a Git clone or checkout, then
=check=: Git preserves neither empty directories nor read permissions or write bits.
Of an archive a keeper keeps repair looks at the ledger events alone
and creates no local archive. A check counts a write bit on an archive's
files only: see =writable= below.

** Check

For each archive found, in path order compared component by component,
a report:

- =archive=: its path; =head=, =events= and =files=;
- =kept=: its keeper's URL, or =null= for an archive on disk;
- =keeper=: what its keeper holds, or =null= for an archive on disk or
  a keeper not asked: =head= and =events= as the keeper describes them,
  and =erased=, the paths the ledger enrols, files and directories, whose
  CIDs the keeper says it has erased, sorted;
- =missing=, =changed=, =new=: enrolled paths absent, enrolled paths
  whose entry differs, and unenrolled paths, each sorted. A schema 2
  entry differs if the file's CID does, too;
- =writable=: the archive's files with any write bit, sorted. A ledger event
  or a checkpoint with one is not a finding. Each is named by a hash
  of its bytes, which the check holds it to, and Git keeps no write
  bit, so every clone has them writable;
- =root=: the archive's CID now, or =null= if IPFS would shard a
  directory in it; =recorded_root=: the recorded root, or =null=;
- =hidden=: files with a hidden component, other than within legacy
  ledger and checkpoint directories, sorted; sealing refuses them;
- =undeclared=: collections the ledger lists whose =README.org= no longer
  declares them, sorted.

A root differing from the recorded root shows a change since sealing
that no file shows, such as an added directory. For a schema 3 ledger
the recorded root is the fold of what it enrols, so the two agree when
the archive holds that and nothing else.

An archive a keeper keeps is reported from its ledger, there being
nothing on disk to compare: =files= counts its entries, =root= is the
fold's, =hidden= is what the ledger enrols under a hidden name, and
=writable=, =missing=, =changed=, =new= and =undeclared= are empty.

Its keeper is then asked to describe what it holds
(=doc/remote-archive-protocol.txt=), with the bearer token in the
environment's =POS_ARCHIVE_TOKEN= if set, unless =POS_ARCHIVE_OFFLINE= is
set to anything, when no keeper is asked. What a keeper refuses refuses
the check, by its kind. A keeper whose =head= is not the ledger's holds
another ledger, or more or less of this one: that is a finding, and
sealing brings the ledger up to date or refuses. What a keeper has
erased is not a finding: the ledger still says what was sealed.

Fixtures: =fixtures/ledger/=: inventories with their first event,
ledgers valid and refused, in both layouts and all three schemas, and
reports, of archives on disk and kept by a keeper. A report fixture
with =keeper= is checked asking that recording, as a seal's is sent to
one ([[*To a keeper][To a keeper]]); every other is checked asking no keeper.

* Sealing

Everything enters an archive by sealing, in two steps: a plan, which is
reviewed, then its application. The reviewer names the plan by the
SHA-256 of its canonical JSON; application refuses any other.

** Plans

=seal SOURCE DESTINATION= plans to move SOURCE, a file or directory
outside any archive, to DESTINATION, a path that does not yet exist inside
an outermost =archives/=, which itself need not exist yet. =write-new
DESTINATION= first stages new bytes in =_seal/= beside the archive, in a
file with DESTINATION's extension, then plans the same way, reading their
links as written from DESTINATION; if planning fails, the staged file is
removed, and =_seal/= with it if left empty. A plan holds, in
canonical JSON:

- =schema=: 2; =operation=: =seal=;
- =source=, =destination=, =archive=, =ledger=: absolute paths, the archive
  and ledger folder resolved; the ledger folder is the archive's, or for
  an archive without one, =archive-integrity/ledger/= beside it;
- =number= and =previous=: the event to be written and the head it
  follows, =null= for none;
- =ledger_id=: the ledger's, else the one its scope's entry names, else
  one supplied, else a random version 4 UUID;
- =add=: the item's files by path within the archive, each a schema 2
  entry of its bytes once its links are rewritten: =cid=, =mode= less write
  bits, =sha256=, =size=;
- =links=: every path link in the item, sorted by file then offset: =file=,
  =offset= in bytes, =from= and =to= the link's text before and after, and
  =kind=, =cid=, =rumour=, =internal= or =broken=;
- =originals=: the SHA-256 of each file whose links change, as it is;
- =rumours=: the rumour records to seal first, sorted by destination:
  =destination= within the archive, =text= and =cid=;
- =collections=: the directories in the item, itself included, whose
  =README.org= declares them, sorted;
- =inventory_sha256=: the SHA-256 of the archive's inventory, in
  canonical JSON, as planned;
- =kept=: for an archive a keeper keeps, the keeper's URL; for one on
  disk the key is absent.

For an archive a keeper keeps, the inventory is what its ledger enrols
and nothing is compared with disk.

Planning refuses: =source= (missing, or already archived), =destination=
(not in an archive, existing, or unsafe), =sealed= (the destination lies
within an item or collection already sealed: a sealed item never grows), =hidden= (a hidden file in the
item, or a hidden destination), =link= (a symlink or second hard link in
the item), =differs= (enrolled evidence in the archive is missing or
changed), =kept= (a keeper keeps the archive, and its ledger is not yet of
schema 3 or it still has files on disk), =identity= (the ledger, or the
id supplied for a new one, is not the one the scope's entry names), and
for links, =unsealed=, =unresolved= and =loop=, below.
Hidden or unenrolled files already elsewhere in the archive do not stop a
seal; the check reports them.

** Links

Links are sought in the item's files, other than a capsule's, named
=*.org=, as Org parses them:
links of type =file=, in any form, their search options kept; and named
=*.md=, as markdown-mode finds them: inline links and images, and
reference definitions, outside code, their fragments kept, their paths
URL-decoded. A Markdown URL with a scheme is not a path.

Each link's path is taken from the file where it was written, before the
move, and resolves:

- within the item: in a collection holding both files, the link stays as
  written (=internal=); to another file of the item, it cites that file's
  CID, taken once that file's own links are rewritten (=cid=); links among
  an item's files that form a loop are refused (=loop=); anything else
  within the item is refused (=unresolved=);
- to a path in the archive of the item's scope, or of a scope within it:
  =ipfs://= and the CID of the sealed item holding it, else of the
  collection holding it, else of the enrolled file itself, then =/= and
  the path within it if it is not the whole (=cid=); a path never sealed
  is refused (=unsealed=). In an archive a keeper keeps, a path its
  ledger folds to is such a path though nothing is on disk, and the CID
  is the fold's;
- to anything else that exists, canon, another scope, or a container's
  archive, since a scope does not depend on its container: a rumour
  record, sealed first as an item of its own, whose CID the link cites
  (=rumour=);
- to nothing: kept, annotated as broken (=broken=). The annotation
  replaces the whole link: in Org the link's type becomes =broken:=, as
  =[[broken:PATH][TEXT]]=; in Markdown the link becomes =TEXT [broken
  link: PATH]=.

A resolved link's target is replaced whole: in Org the raw link, as
=ipfs://CID/PATH::SEARCH=; in Markdown the URL, as =ipfs://CID/PATH#FRAGMENT=.

=link PATH= prints the link to PATH, a path in an archive, as a sealed
item's link to it is rewritten: =ipfs://=, the CID and the path within
it, on one line. A path never sealed, or in no archive, is refused
(=unsealed=). It reads the archive and writes nothing.

=fetch LINK= prints the bytes of the file LINK names, =ipfs://CID= or
=ipfs://CID/PATH=, and nothing else. PATH ends where an Org search
begins, at =::=. Each scope above the current directory that has an
archive is tried, nearest first: the file is the one at PATH beneath
whatever the scope's archives hold under CID, or that itself. A file on
disk is read as it lies, which a check and not this command holds to
its ledger. A file a keeper keeps is read from the keeper
(=doc/remote-archive-protocol.txt=) by the CID its ledger enrols, and
bytes that are not that CID's are refused (=entry=); what the keeper
refuses is refused by its kind. A directory, a CID no such archive
holds, and text that is no link are refused (=absent=).

A rumour lies at =rumours/DATE-HASH.org= in the archive, HASH the first 12
hex digits of the SHA-256 of its text, DATE the plan's; one rumour serves
every link to its target from the item, and rumours of one target that
differ in word differ in name. Its text is:

#+begin_example
,#+TITLE: Rumour of PATH
,#+DATE: DATE

On DATE, sealing =ITEM= found a link to =PATH=, outside the archive. It was then DESCRIPTION.
#+end_example

DESCRIPTION is =outside the garden, and was not read= for a target beyond
the garden's repository, which is never read; else =a directory=, or =a
file of N bytes, SHA-256 =HEX== with
=, titled "TITLE"= if the file has an Org =#+TITLE= or a Markdown =#=
heading. A rumour already sealed, word for word, is cited, not sealed
again; one differing at its destination is refused (=destination=). In
an archive a keeper keeps, a rumour is sealed already when the ledger
enrols its destination with its CID.

Planning an item that holds Org or Markdown files is poslib's, since Org
interpretation is; pyposlib refuses to plan it (=interpretation=), and
applies any plan.

** Application

1. The plan's hash must be the one reviewed, else =plan=.
2. The events since the plan's =previous= must seal a prefix of its
   rumours, then its item, in order, else =plan=; before any, the archive's
   inventory must be as planned.
3. Each rumour not yet sealed is published at its destination and sealed:
   an event whose =item= is the rumour and whose =add= is its entry.
4. Unless the item has moved already, each file in =originals= is
   rewritten where it lies, its links replaced at their offsets, unless it
   has been already; each empty directory named =_seal= in the item, a
   staging directory left behind, is removed; hidden directories and
   nested =archives/= are not entered, nor are symlinks followed. The
   item's entries must then be as planned, else
   =plan=; then the item moves to its destination in one rename, and
   the directory it lay in is removed if it is =_seal= and left empty,
   as a record staged by =write-new= leaves it.
5. The item's entries at the destination must be as planned, else =plan=.
6. Unless sealed already, its event is written: =previous=, the ledger's
   head; =ledger_id=, =add= and =collections= from the plan; =item=, the
   destination's path within the archive; and =root=. In a ledger with
   no event yet, or whose head is a block, the event is of schema 3,
   with =empty= as found in the item where it now lies. In a ledger of
   schema 1 or 2 it is of schema 2, its =root= the archive's CID now,
   until the ledger is converted.
7. Write bits are removed from the item's files and the rumours; events,
   like every ledger and checkpoint file, have mode =0444=.
8. A checkpoint of the archive's head, of coverage =archive=, is written
   beside the archive: in =archive-integrity/checkpoints/= if
   =archive-integrity/= exists there, else in the legacy folder.

Applying a plan again after an interruption finishes it, and after
completion changes nothing.

A program that seals or writes records itself, with no one to review each
plan, uses =seal SOURCE DESTINATION --apply= or =write-new DESTINATION
--apply=: it plans, applies that plan at once
under its own hash, and prints =plan=, =hash=, =event= and =root=. The
plan and its refusals are those of the two-step form.

*** To a keeper

A plan with =kept= is applied to its keeper, over
=doc/remote-archive-protocol.txt=, and nothing is written to
=archives/=. A plan is refused (=plan=) unless its archive is kept now
as the plan says: by that keeper, or on disk for a plan without the key.

1. The plan's hash must be the one reviewed, else =plan=.
2. The keeper is asked what it holds. It must hold this ledger: as many
   events, with the same head; or more, in which case the events the
   ledger lacks are fetched by number and written to it, and the ledger
   must then be valid and end at the keeper's head. Anything else is
   refused (=chain=), with the ledger as it was. A seal interrupted
   after its keeper took an event is finished this way, and so is a
   ledger behind because another clone sealed.
3. As step 2 above, the inventory being what the ledger enrols.
4. Each rumour not yet sealed is sent: an event whose =item= is the
   rumour and whose =add= is its entry, of mode =0444=, with the one
   file its text is.
5. Unless its event is in the ledger, the item's files in =originals=
   are rewritten where it lies, its staging directories left empty are
   removed as in step 4 above, its entries must be as planned, else
   =plan=, and its event is sent with every file it enrols. The event
   is as in step 6 above, of schema 3, =empty= as found in the item
   where it lies.
6. An event is written to the ledger once the keeper has answered that
   it holds it, and not before. What a keeper refuses is refused by its
   kind, and nothing is written.
7. The item is then removed from where it lay, if its entries are still
   as planned, else =plan=, and the directory it lay in as in step 4
   above.
8. The checkpoint, as step 8 above.

With each event the client sends its claims, strings by name, which a
keeper records and does not verify:

- =plan=: the plan's hash; =tool=: =poslib= or =pyposlib=; =tool_commit=:
  the commit the tool is at, where it knows it: from the =COMMIT= file an
  image writes at the tool's root, else from git where the tool is a
  checkout;
- of the scope's repository, where there is one and git reads it:
  =scope=, the scope's path in it; =commit= and =branch=, where its
  =HEAD= is; =dirty=, =true= or =false=, whether git reports anything
  changed or untracked; and =remote.NAME= for each remote, its URL less
  any user and password.

The keeper is reached with the bearer token in the environment's
=POS_ARCHIVE_TOKEN=, if set.

Fixtures: =fixtures/ledger/seal-*=: a tree, a source and destination, a
date for rumours, and the plan, the last event and the report after it,
paths relative to the tree; or the refusal. A fixture sealed to a keeper
has =keeper=, the keeper's =url=, a =token= and the =exchanges= in order,
each a =request= and a =response= as a tape of
=doc/remote-archive-protocol.txt= has them, and =claims=, sent in place
of the client's own. A client makes each request as recorded and no
other, and the item is gone afterwards unless the seal was refused. The
report after a seal is made asking no keeper.

** Keeping

=keep ROOT= moves to its keeper each archive under ROOT whose scope's
entry says a keeper keeps it and whose files are still on disk, the
state the check refuses as =kept=. An archive with no keeper, no ledger,
or no file on disk is left, with the reason: =on disk=, =no ledger= or
=kept=.

Before anything is sent, every archive to be moved must have: the ledger
its entry names, if it names one (=identity=); a head that is a schema 3
event (=kept=); its ledger beside it and not in the legacy folder inside
(=ledger=); nothing missing, changed or new, with its CID both the
recorded root and what its ledger folds to (=unclean=); and no hidden
path enrolled (=hidden=), since a keeper holds no hidden file.

Then, for each archive:

1. The keeper is asked what it holds. It must hold the ledger's first
   events and no other: no more events than the ledger has, its head
   naming the ledger's event of that number; else =chain=.
2. Each event it lacks is sent in order, as its ledger file's bytes, with
   the files that event enrolled and the ledger still enrols. They are
   read from the paths they have now, since a schema 2 conversion may
   have renamed or removed what an earlier event enrolled, and each is
   named by the CID the ledger enrols it under. No file is sent twice in
   one run.
3. A first event that names no ledger, as those of a ledger begun
   before events carried a =ledger_id=, is sent with the events after it
   in the ledger, up to and including the first that has one. By them
   the keeper knows whose the event is
   (=doc/remote-archive-protocol.txt=, section 3). An event that has a
   =ledger_id=, or follows one that has, is sent alone.
4. A keeper that already holds earlier events is taken to hold their
   files, sent with them by the run that sent the events. If it refuses
   the first schema 3 event as =entry=, the event at which a keeper
   requires every file enrolled before it, that event is sent once more
   with all of them.
5. The keeper is asked again, and must describe the ledger's head, its
   number of events and its recorded root; else =chain=.
6. The archive is removed from disk, its empty directories with it. The
   ledger and its checkpoints are unchanged.

The claims sent with each event are a seal's, without =plan=. What the
keeper refuses is refused by its kind, with the archive still on disk.

Run again after an interruption, it sends what the keeper still lacks. A
keeper limits what one append may hold (=size=). Files travel with the
events that enrolled them so that an archive larger than that limit can
be moved; one event's files larger than it cannot.

It prints =kept=, each an =archive= with its =keeper= and the =events=
and =files= sent, and =skipped=, each an =archive= with its =reason=.

Fixtures: =fixtures/ledger/keep*=, of kind =keep=: a tree, the =root=,
=claims= and a =keeper= as a seal to a keeper has them, and =kept=,
=skipped= and the report after, made asking no keeper; or the refusal.

** Recalling

=recall ROOT= brings back from its keeper each archive under ROOT whose
scope's entry says a keeper keeps it: the reverse of =keep=. A scope that
retires is recalled first, so that its container seals its files. An
archive with no keeper or no ledger is left, with the reason: =on disk=
or =no ledger=.

Before any keeper is asked, every archive to be brought back must have:
the ledger its entry names, if it names one (=identity=); a head that is
a schema 3 event (=kept=); a ledger that folds to its recorded root
(=root=); and nothing on disk that the ledger does not enrol or that is
not as enrolled, its mode included (=differs=).

Then, for each archive:

1. The keeper is asked what it holds, and must describe the ledger's
   head, its number of events and its recorded root; else =chain=.
2. Each enrolled file the disk lacks is read from the keeper by the CID
   the ledger enrols it under, in order of path, one read serving every
   path of that CID. Bytes that are not that CID's are refused
   (=entry=). The file is written at its path, with its recorded mode.
3. Each empty directory the ledger records is made.
4. The archive's CID must then be the recorded root; else =root=.

What the keeper refuses is refused by its kind, erased bytes as
=erased=, with what was already written left on disk. Run again, it
reads only what the disk still lacks. The keeper is sent nothing and
holds what it held.

The archive is then on disk as its ledger says, and its entry still
says a keeper keeps it: the state the check refuses as =kept= and =keep=
begins from. Changing the entry is the person's to do.

It prints =recalled=, each an =archive= with its =keeper= and the
=files= read, and =skipped=, each an =archive= with its =reason=.

Fixtures: =fixtures/ledger/recall*=, of kind =recall=: a tree, the
=root= and a =keeper= as a seal to a keeper has them, and =recalled=,
=skipped= and =after=, the archive's files and empty directories as a
fixture tree lists them; or the refusal.

** Conversion

=convert ROOT= brings every schema 2 ledger found under ROOT to schema 3
by the conversion event, and checkpoints each new head. It adds nothing
to an archive, so there is no plan to review. Every archive is verified
before any event is written: one with a file missing, changed or
unenrolled, or whose CID is not the root its ledger recorded, refuses
the whole (=unclean=), as does one whose ledger does not fold to that
root (=root=). An archive with no ledger, a ledger already of schema 3,
and a ledger holding legacy entries, which migration converts first, are
left and reported with the reason. It prints =converted=, each an
archive with its =event= and new =head=, and =skipped=, each an archive
with its =reason=. Applied again, it finds its work done.

Fixtures: =fixtures/ledger/convert*=: a tree and a root, and the events
written, what was skipped and the report after; or the refusal.

* Migration

The one sanctioned rewrite of archived bytes: an archive whose ledger
holds legacy entries is rebuilt, in content identity, and its ledger
closed by a conversion event. Migration is poslib's, as planning links
is.

A plan, reviewed and applied as a seal's is, describes the rebuilt
archive:

- =discard= and =remove=: Finder's =.DS_Store=, unenrolled and enrolled;
  =remove= also holds enrolled paths missing already;
- =renames=: in order, a legacy ledger folder within the archive to
  =archive-integrity/ledger/= beside its archive, a legacy checkpoint
  folder to =archive-integrity/checkpoints/=, and any other hidden entry
  to its name prefixed =dot=, keeping its bytes;
- =collections=: the receipts (with =manifest.json= and =source/=),
  capsules (in =capsules/=), runs (in =trials/=, =studies/= or
  =pipeline-trials/=), retired scopes (holding =archives/=) and capsules,
  none within another, less those the reviewer excludes and with those
  the reviewer includes, which their shape does not show;
  =declarations=: each but a capsule declared in its =README.org=, the
  line added after its leading keywords, or a new =README.org= made,
  naming the collection's entrance;
- =rumours=: at =rumours/DATE-HASH.org=, as for sealing, the text saying
  that migrating the archive found links to the path;
- =links=: every link, as for sealing, from where it was written, with its
  resolution; a scope within this one must be migrated first, and a
  container's archive is cited by rumour; a link to a path gone from the
  archive whose counterpart at the same relative path from the scope
  exists means the counterpart: a withdrawn record's in canon, cited by
  rumour, or a record's archived since the link was written, cited by
  CID. Each link has its edit: =cid=, =internal=, =rumour=, =broken=, annotated, or =later=, a
  link from an earlier item to a later one where items' links loop,
  annotated =[[later:PATH][TEXT]]= in Org and =TEXT [later record: PATH]= in
  Markdown; an item's date is one its path begins with, else its first
  commit's;
- =canon=: each canon file under the plan's root with links to a path the
  migration moves, its SHA-256 and the edits repairing them;
- =inventory_sha256= and =final_inventory_sha256=: the archive before and
  after; =event=: the conversion event's name and text.

Applying the plan rebuilds the archive in =_migrate/= beside it, refusing
any difference from the plan, keeps the archive as it was there, swaps
the rebuilt archive in, moves the ledger and checkpoints beside it,
writes the conversion event, removes write bits, repairs canon and
checkpoints the head. Applied again, it finds its work done.

* Fixture trees

A fixture's =tree= lists entries by =path=, one of:

- =text=: a file of that string's UTF-8 bytes;
- =repeat=: =[BYTE, COUNT]=, a file of COUNT copies of BYTE;
- =pattern=: =N=, a file of the bytes =i mod 251= for =i= below N;
- =series=: =N= with =text=, N files, =path= holding =%04d= for the index;
- =directory=: true, an empty directory;
- =symlink=: a target; =hardlink=: another entry's path.

=mode= sets a file's permission bits, default =0644=.
