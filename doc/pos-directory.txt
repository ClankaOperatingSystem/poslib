The configuration directory
Version 2

A personal operating system is a tree of responsibilities: a root, and
beneath it responsibilities, each of which may hold more, with projects
and products as its leaves. Each is a node. A node is a directory of
the repository that holds it, or a repository of its own, shared with
other people and checked out in place within the tree. This document
says how a node declares what is beneath it and what it needs
configured, in a configuration directory at its root, and what a tool
does with those declarations.

It names no server. poslib and pyposlib read the configuration, and a
server a node names is whichever its owners run. Everything here but
section 5 works with no server at all.

Version 1 of this document is not read: a file that says pos: 1 is
refused, and is rewritten to this version.


1. The file

A node's configuration directory is named .pos. One named .clanka or
.clankos is read as well, and means the same: those are the names
ClankOS gives it. In it the configuration is config.yaml or config.yml,
which mean the same too. It is committed with the node. A node has one
configuration: two directories, or two files in one, are refused
(two-configurations). A
directory without one declares nothing, and what kind of thing it is
follows from that (section 2).

The file is YAML: mappings, sequences and scalars. It uses no anchors,
aliases, tags or second document, and a mapping holds a key once; what
a reader makes of a key written twice is not defined.

A reader takes every scalar as the text written and guesses no type
from it, quoted or not. YAML libraries differ over what a bare word
is, and one that resolves types may resolve a quoted word too. The
keys below say what each value is:

    a string    any text but the empty one, null and ~
    an integer  a whole number in digits, with no leading zero

So a branch named 1.10 or no is that text, and a value left empty is
refused.

The top level is a mapping:

    pos             2, the version of this document; required
    projects        where this node's projects belong: a path beneath
                    it, usually projects/. What lies directly there is
                    a project (section 2)
    methodologies   the methodologies and other skills repositories
                    whose skills are installed in this node: a
                    sequence of sources (section 6). Or a path beneath
                    the node, usually methodologies/, where each
                    methodology is a child declared directly beneath
                    it (section 2)
    harnesses       the coding agents the skills of the sources are
                    installed for (section 6)
    image           the container image this node's commands run in
    bin             where links to this node's commands are made
                    (section 6): a path beneath it, usually bin
    exclude         the directories a walk of this node does not enter
                    (below)
    children    what is declared beneath this one (section 2)
    worktrees   other working trees (section 3)
    archives    where archives are kept (section 4)
    keeper      the keeper of this node's archives (section 4)
    server      the server this repository is bound to (section 5)

A node is a responsibility or a project. The file does not say which:
where the node lies does (section 2). A file may have projects,
methodologies, both or neither, so a responsibility may have
methodologies as a project may. Where methodologies is a path, the two
are separate paths: where one is the other, or beneath it, the file is
refused (bad-path).

A reader reads methodologies written as a path, and warns of it as
"methodologies-path: PATH": each methodology the node mounts there can
be declared as a source instead.

A final slash on any of these paths is dropped.

image is written on a line of its own, as "image: NAME" from the start
of the line, with NAME unquoted and holding no space, quotation mark
or #, so that a tool with no YAML reader finds it by its line. Any
other way of writing it is refused (bad-value). A node that names no
image takes that of the nearest node above it in the same repository
that names one. A mounted child does not take its container's: where
nothing in its own repository names one, its commands run in the
tool's default image, wherever the child is mounted.

exclude is a sequence of strings. Each is the name of a directory, or
a glob over one with * for any text, which keeps a walk out of every
directory of that name beneath this node, however deep; or, when it
holds a slash, a path beneath this node, which keeps a walk out of
that directory and what lies beneath it. A name is matched letter for
letter: attic does not exclude Attic, and no character but * stands
for another. A path's final slash is dropped, unless the path is one
name: journal/ is the directory journal of this node and no other,
and keeps its slash to say so. The
exclusions in force at a directory are those of the nearest node at or
above it in the same repository that has the key, replacing what it
would inherit; when no node of the repository has it, they are

    archives, attic, node_modules, "_*", ".*"

that is, archives and attics, Node's modules, and every name beginning
with an underscore or a dot. An empty sequence excludes nothing. A
glob beginning with * is quoted, as YAML asks. What exclude governs is
reading: a tool that walks a node for its files, its undeclared
repositories or its archive scopes does not enter an excluded
directory. A directory named archives is an archive scope wherever it
lies, whether or not the walk enters it. A repository mounted in the
tree is read by its own configuration: the exclusions of the
repository it is mounted in do not reach into it, and one that
declares none has the default.

What passes down:

    Key                          Where a node gets it
    image, exclude, keeper       From its own configuration. If that
                                 has none, from its parent's, and so on
                                 up to the configuration in the
                                 directory that holds .git.
    server                       From the configuration in the
                                 directory that holds .git.
    projects, children,          From its own configuration only.
    worktrees, bin, harnesses,
    methodologies

A mounted repository does not read the configuration of the repository
it is mounted in.

A reader reads the keys written here. A key it does not know, at any
level, is a warning, which names the key by its place in the file, as
"unknown-key: children[0].pin"; the key is left unread and the rest of
the file is read. So a file written for a newer version of this
document is read by an older reader with the newer key's default,
which is always what the older reader did. The version number changes
only when a key's meaning changes.

A reader refuses the whole file for a version it does not know, and
for a value it cannot read. A refusal has a kind:

    not-yaml          the text is not readable as YAML
    not-a-mapping     the file, or an entry, is not a mapping
    unknown-version   pos is a number other than 2
    missing-key       a required key is absent
    wrong-type        a value is not of its key's type
    bad-path          a path this document does not allow
    bad-value         a value this document does not allow
    two-configurations  the node has more than one configuration

The file holds no credential. What a person signs in with is theirs and
stays out of a repository other people share.


2. Children

children is a sequence. Each entry is a mapping:

    path        where the child is, relative to this node
    remote      the git remote it is cloned from; absent for a child
                that is a directory of this node's repository
    branch      with remote, the branch its working tree rests on;
                master when absent

An entry is a boundary. Its path and everything beneath it is the
child's and not this node's. The entry does not say what the child is;
where it is, and what is at the path, do:

    directly beneath the node's methodologies path,
    where methodologies is a path                        a methodology
    no configuration                                     a product
    a configuration, directly beneath the node's
    projects path                                        a project
    any other configuration                              a responsibility

A directory or an Org file directly beneath a responsibility's
projects path that no entry declares is a project too: one with no
configuration, which declares nothing. So a project is known by its
place, and what its configuration holds, if it has one, does not say
that it is one.

A responsibility is a branch of the tree: it declares children of its
own, each node naming only what is directly beneath it. A project is a
leaf: it holds no responsibility or project. Its children are its
methodologies, each directly beneath its methodologies path, and
products it works on, anywhere else beneath it. A project's
configuration that says where projects belong is reported
(project-holds-projects), and what lies there is the project's own. A
product is a subject, under its own rules, and this document says
nothing of what is in it but this: its Org files are read as the
product's.

Where methodologies is a path, a methodology mounted beneath it is a
repository or a directory that supplies skills and commands to the
node that declares it, a project or a responsibility (section 6). Its name is the last part of its path:
methodologies/hello is the methodology hello. Nothing at the path
says it is one; the entry's place does, so the same repository is a
methodology where a node declares it beneath
its methodologies path and a product wherever else it is declared,
mounted as often as there are entries for it, each on its own branch.
A methodology's path has exactly one part after the methodologies
path: an entry at that path itself, or deeper beneath it, is refused
(bad-path). The name clankos is reserved: an entry whose methodology
is named clankos is refused (bad-value).

A tool that walks a node for its files does not enter a
methodology, whether it is a directory of the node's repository or
a repository mounted there: a methodology's own files are not the
node's canon. What a methodology holds, and the kinds of canon it
declares, are in doc/pos-methodology.txt.

A tool that walks a tree for its Org files follows the declarations: a
parent knows its children, and a child knows nothing above it. From a
node the walk enters the ordinary directories of the node and each
child the node declares, whatever the child is. A child with a
configuration is a node and is walked as its configuration says. A
child with none is a product: its Org files are read as the product's,
each file in its place, with the default exclusions (section 1)
whatever the declaring node excludes. A repository within a product is
not entered, and a configuration within one makes no node. What a child
is does not decide whether it is read; a methodology alone is not
entered. A directory with a configuration that no node declares is not
in the tree: the walk reports it and does not enter it. Reading changes
nothing about writing: only the files of the repository the tool is
run in are written. A file that may not be written keeps its own
#+TODO line.

path is any path that stays beneath the node: relative, with no empty
part and no part that is . or .., and no backslash. No folder name
carries meaning. It does not pass through another child: what is
beneath a child is the child's to declare.

A child with a remote is a repository checked out in place. branch is
the branch the work is based on. That is usually the repository's
default branch. For the length of a feature branch that takes many pull
requests it is that branch, and the entry is changed back afterwards.

The repository that holds the declaring node does not track such a
child. Its path is written to that repository's .git/info/exclude
before the child is cloned, since staging everything in a container
records an unexcluded child as an embedded repository. The line written
for a path is the path from the repository's root with a slash before
it, which anchors it there.

A child with no remote is a directory of the same repository, tracked
and committed with it. It has no branch, and an entry that gives it
one is refused (bad-value). Nothing is excluded or cloned for it. What
its own configuration declares is declared for the repository it is
part of.

A responsibility's one-file projects are Org files where its projects
belong, and no entry declares them: making the file is the commitment.
A project that needs a directory is given one, with a configuration,
and is then declared.


3. Worktrees

worktrees is a sequence of working trees that are not scopes: a
repository that does not follow this layout, or a branch other than the
one a child rests on. Each entry is a mapping:

    path        where it is checked out, relative to this node:
                PATH/_worktrees/NAME, or _worktrees/NAME, where PATH
                is beneath the node and not in a child
    of          the path of one of this node's children that has a
                remote: the working tree is a git worktree of that
                child's clone
    remote      in place of of: the git remote it is cloned from, a
                clone of its own
    branch      the branch it rests on; required with of, master when
                absent with remote

A working tree beneath _worktrees is disposable once its commits are
pushed. Its path is written to .git/info/exclude as a child's is. The
commits of a git worktree are in its child's clone, so it is that clone
whose unpushed branches matter.


4. Archives

archives is a sequence saying where an archive is kept. An archive
belongs to a scope: the directory that holds it. Each entry is a
mapping:

    scope       the scope's path beneath this node, not in a child;
                "." is the node itself
    kept        committed: on disk and committed with the repository
                uncommitted: on disk and not committed, its path
                ignored by Git
                remote: by a keeper (doc/remote-archive-protocol.txt)
    url         with remote, the base URL the keeper gives the scope's
                ledger; absent, the node's keeper with the ledger's
                id in it
    ledger      the id of the scope's ledger, a UUID in canonical form
                with lower-case letters; optional, with any kept
    sweep       how the scope's done items are retired (below):
                weekly or sealed; optional
    path        with weekly, where the weekly archive files are written,
                a path beneath the scope; default archive/orgmode

keeper is a URL. The client replaces {ledger} in it with the ledger's
id. A scope no entry names is kept remote by the keeper its node gets
(section 1). If no configuration in the repository names a keeper, the
archive stays on disk and Git ignores it. In every case the
ledger stays with the scope and is committed.

The sweep retires the done items of a scope's Org files each week. An
entry's sweep says how: weekly writes them into Org archive files
beneath the scope, at path, one directory for each ISO week and
within it one file for each source, named by the source's path within
the scope with _archive appended; sealed writes the week's files the
same way beneath _sweep/ in the scope and seals a week's directory
into the scope's archive at sweep/WEEK, on disk or with the scope's
keeper as kept says, so that finished work has the same standing as
any sealed item. A week's directory is sealed once sweeps no longer
write into it. A sweep writes into the directory of the latest week
to have ended, at Sunday 23:00 local time, and goes on doing so until
the next week ends; so that directory is sealed after the following
Sunday 23:00, and an earlier week's at any time. A file is retired by
the nearest entry with sweep at or above the scope it belongs to,
within the same repository; when none has one, it is retired weekly
beneath the root of its repository, at the default path, as before
there was a choice. A sweep that is not weekly or sealed is refused
(bad-value); a path with any sweep but weekly is refused (bad-value),
as is one that climbs (bad-path).

The entry for an archive is looked for in the nearest node at or above
its scope: the nearest directory with a configuration.

The tree tool maintains a marked block in each repository's
.git/info/exclude for its uncommitted archives. It covers each declared
node, each explicitly named archive scope (even before its directory
exists), and other scopes found by their archives directories. It
does not enter the directories the node's exclusions name (section 1),
undeclared nodes, or products. A declared child reads its own policy;
a parent's default does not override it.

Patterns are anchored at the repository root, match directories only,
and quote spaces and Git glob characters. When a policy changes, the
block is replaced, leaving all rules outside it alone. Committed and
remote archives get no exclusion from this block. A damaged block,
symbolic link at an archive path or exclude file, or a refused local
node configuration is reported and leaves the repository's block
unchanged. The tool does not remove files from Git's index; already
tracked files stay tracked. Existing user ignore rules, including
/archives/ written by earlier initiate versions, stay as they are.

A ledger otherwise draws its id when its first event is made. A keeper
may be bound to a ledger's id before that event exists, so an entry can
say what the id is. An entry whose ledger is not such a UUID is refused
as bad-value, and so is a file in which two entries name one ledger.


5. The server

server binds a repository to a server its owners run. It is read from
the configuration at a repository's root. It is a
mapping:

    name        what a coding agent knows the server by
    mcp         the URL of the server's MCP endpoint

Absent, the repository is bound to none.

A binding covers its own repository. The server is configured for
sessions started in this repository, and for none in a repository
mounted in it or containing it.

For each coding agent a tool supports, it writes the file that agent
reads for MCP servers, in this repository. The files are untracked,
with their paths in .git/info/exclude, and a file the repository
tracks is left as it is. Nothing is written outside the repository.


6. What is installed

The tool installs skills and commands in each repository of the tree
that has a configuration at its root: the root's, and each mounted
responsibility's and project's. A coding agent looks for skills from
where a session starts up to the root of that repository and no
further, so a session started anywhere in such a repository finds
what is installed at its root, and finds the same in each.

Nothing is installed in a product, and nothing in a product is
written, linked or changed; its Org files are read (section 2). A product's skills are its own. So are the skills a
repository keeps besides those installed: the tool links none of them
into another repository.

The tool is given a directory to install from, the source:

    version        one line, which names what the source holds
    repository     one line, the git URL of the repository the source
                   was made from
    commit         one line, the full forty-digit id of the commit it
                   was made from
    skills/NAME/   a skill: a directory holding a SKILL.md, whose NAME
                   begins "clankos-", or is a slot's name
    bin/NAME       a command

The slots are capture, start-up and wrap-up, as doc/pos-slots.txt has
them: a skill and a command of each name, which a repository may
supply itself. Given no source, the tool installs nothing, and keeps
the links below to what is already installed. A source that names no
version, no repository or no commit by its full id, or holds a skill
named otherwise, is refused (bad-source).

In the configuration directory at a repository's root, auto/ is the
tool's alone. Where it is absent, or its version is not the source's,
it is replaced whole by a copy of the source. It is untracked, with its
path in .git/info/exclude. What anyone else writes in it is lost.

Links make the commands found:

  - For each command in auto/bin/, where the node at the repository's
    root says bin, NAME in that directory is a link to it.
  - A link is a relative symbolic link. It is untracked, with its path
    in .git/info/exclude.
  - A link is the tool's if it is a symbolic link whose target is in
    auto/ of the repository it is made in, or beneath the methodologies
    path of the node it is made in. The tool's link to something no
    longer there, or into a methodology no longer declared, is removed.
    So a skill or a command a newer source leaves out goes, and its
    link with it.

Where the path of a link the tool would make holds anything else, a
file, a directory or another link, the tool leaves it as it is and
reports it (name-taken), saying whether the repository tracks it and,
if so, the commit that added it. The other links are made. A coding
agent may take what holds the name for the skill it was to find, so
the finding is reported until the name is free. A slot's name is the
exception: what holds it, tracked or not, is the repository's own
filling of the slot, so the tool makes no link there and reports
nothing. Where .agents or
.agents/skills is a file or a symbolic link, no skill link is made in
that repository, and that path is reported the same way; so is a part
of the path a node names as bin.

A coding agent that reads .claude/skills is served too:

  - Where the repository has skills in .agents/skills/, .claude/skills
    is absent, and .claude is absent or an ordinary directory, a link
    to ../.agents/skills is made, untracked and excluded.
  - Where .claude/skills is an ordinary directory, the tool makes its
    skill links there as well, each to the skill it links from
    .agents/skills/, and writes
    beside them a note, README.clankos, untracked and excluded. The
    note says that the directory's skills can be moved to
    .agents/skills/ and the directory replaced by a link to it, lists
    each entry that is not a directory holding a SKILL.md, and so is
    no skill, and names where that convention is described. A note
    the repository tracks is not the tool's, and is reported as a
    name taken. Once .claude/skills is no longer an ordinary directory
    the note is removed from .agents/skills/, where it went if the
    directory's entries were moved there.
  - A .claude or .claude/skills that is a file or a symbolic link is
    left as it is.

A link an earlier version of this document had the tool make, an
untracked symbolic link in .agents/skills/ whose target is a skill's
directory in another repository of the tree, is removed: in a product
too, since the tool made it.

A node's methodologies supply skills and commands in the same way,
from where they lie. A methodology is a directory holding

    skills/NAME/   a skill: a directory holding a SKILL.md, whose NAME
                   begins with the methodology's name and a hyphen
    bin/NAME       a command

either of which may be absent. Nothing is copied: for each skill,
.agents/skills/NAME is a link to it in the methodology's directory,
and for each command, where the node says bin, NAME there is a link
to it. The links are made as the links above are, relative, untracked
and excluded, and .claude/skills is served the same way. They are made
in the node: at the root of its repository, beside the source's
links, when the node is a repository; in its directory, when it is
a directory of a repository. The methodology is whatever is at its
path: a change to it is seen on the next plan, and nothing is
versioned.

A methodology that holds a skill whose NAME does not begin with the
methodology's name and a hyphen is reported (methodology-refused) and
nothing of it is linked; the node's other methodologies and the
source's skills are. Where a methodology's skill or command has the
name of one of the source's, or of another methodology's, the path is
held by the tool's own link to the first, and the second is reported
(name-taken) as any other is. A methodology not yet cloned is cloned
as any child is, and its links are planned on the plan that follows.

Nothing is installed in a methodology and nothing in it is changed:
the tool reads its skills and commands and writes only links in the
node that declares it.

A coding agent shows a session the skills of the directory it is
opened in and of each directory above it, as far as the root of the
repository. So the skills of a node's methodologies are shown in every
directory beneath that node in the same repository, a project that is
such a directory among them, and in no repository mounted there. A
project that is a repository of its own is shown none of its
responsibility's.

Where a directory's .agents/skills holds a skill with the name of
another skill in a directory above it in the same repository, an agent
shows one and not the other, or two under one name. The tool reports
the lower (name-repeated) with the path of the upper. Two whose
SKILL.md are the same text are one skill, as when one methodology is
declared at two nodes of a line, and are not reported. The directories
the exclusions in force name are not looked in, and nothing is
reported in a product.

A node's sources are the other way skills reach it. methodologies, as a
sequence, holds one entry for each repository of skills the node
installs from, a mapping:

    source      the repository's git URL: SCHEME://HOST/PATH, or
                USER@HOST:PATH for SSH. A private repository is
                given by its SSH URL
    ref         the tag or the commit to install, a commit by its full
                forty-digit id. A branch is not a ref
    skills      a sequence of the names of the skills to install; all
                of the repository's when absent
    kind        methodology, the default, or skills-repository

A source's name is the last part of its URL's path, less a final .git:
https://example.org/team/pr-gnome.git is pr-gnome. A methodology names
each of its skills with its name and a hyphen, as pr-gnome-write does.
A skills repository is one whose skills are named as its owners choose,
such as a third party's, and is exempt from that rule.

Two sources are the same source when they are equal once each has lost
a final slash and then a final .git, and, where it begins
https://github.com/, that beginning. The skills CLI writes a GitHub
repository's source in its lock file in that shorter form.

A reader refuses (bad-value):

  - a source that is not a git URL of either form, or that begins with
    a hyphen;
  - a ref that begins with a hyphen, or holds a space, # or @;
  - a skill's name that is not words of lower-case letters and digits
    joined by single hyphens, as the Agent Skills specification has a
    skill's name, and an empty skills;
  - a kind other than the two;
  - a methodology whose name is not such a name, or is clankos;
  - a skill that a methodology's entry names without its prefix;
  - one source declared twice, two methodologies of one name, and one
    skill named by two entries.

harnesses is a sequence of the coding agents the skills are installed
for, by the names the skills CLI gives them, such as codex, opencode and
pi. A name is lower-case letters, digits and hyphens, and begins with a
letter or a digit; one that is not, and one named twice, is refused
(bad-value). When harnesses is absent, the skills are installed in
.agents/skills/ alone.

The source's skills are installed as a source's are, and no
configuration declares them. At a repository's root, its node has one
source more, the image's:

    source      the source's repository
    ref         the source's commit
    skills      the source's skills, less a slot's skill that the
                repository fills itself: something is at
                .agents/skills/NAME that is not the tool's link into
                auto/, and that has no entry of the source's
                repository in skills-lock.json

Given no source, the tool takes the image's from what auto/ holds;
where auto/ names no repository or commit, the node has no source
more. A node beneath the root in the same repository has none: a
coding agent shows a session there the skills of the root.

The tool does not install a source: that needs the network, which a
plan does not use. The image's install command does it, as its own
document has it, and leaves in the node

    .agents/skills/NAME/   each skill of the sources, a directory
    skills-lock.json       the skills CLI's record of what it installed

both committed with the node, so that a new clone has its skills with
no command run. skills-lock.json is a JSON object whose skills maps
each skill's name to an entry: source, a sourceUrl where the skills CLI
records one, ref, and other keys this document does not read. An entry
is a declared source's when its sourceUrl, or its source where it has
no sourceUrl, is the same source.

The tool compares a node's skills-lock.json with its configuration,
the image's source counted as declared, and finds:

    lock-differs     a declared source with no entry; a skill that a
                     source's entry names, with no entry from that
                     source; an entry whose ref is not its source's;
                     and a skills-lock.json that is not such an object
    lock-undeclared  an entry of no declared source, such as one the
                     skills CLI wrote when run by hand, or of a skill
                     its source's entry does not name

Each has the path of the skills-lock.json, and a detail:

    SOURCE at REF: not installed
    NAME: not installed from SOURCE
    NAME: LOCKED installed, REF declared
    not a lock file
    NAME: from SOURCE, which is not declared
    NAME: not among the skills of SOURCE

where SOURCE and REF are as the configuration has them, SOURCE is the
entry's source for an entry of no declared source, and LOCKED is the
entry's ref, or "no ref" where it has none. The entries are compared in the order of their names,
then the sources in the order declared, each source's skills in the
order named. A node that declares no sources and has no
skills-lock.json has nothing compared. A repository's own skill has no
entry and is not compared. The lint reports each lock-undeclared
finding too.


7. The two steps

One tool brings a tree to what its configurations declare, in two
steps.

The first step prints a plan: what needs to be done, if anything. It
changes nothing and uses no network. Everything in a plan can be told
from the disk.

The second step is given a plan and does those things and nothing else.
It makes the plan afresh first and refuses, as stale-plan and having
done nothing, a plan the tree no longer gives. If an action cannot be
done it stops and refuses, as failed, and what it did before stays
done. It prints the plan that remains.

A plan holds actions:

    clone       a declared child or worktree that is not there
    exclude     a path to add to a .git/info/exclude
    archive-excludes  replace the managed archive block in info/exclude
    install     a repository's auto/ to replace from the source
    link        a link to a skill or a command, or the .claude/skills
                link, to make
    unlink      a link or a note of the tool's that is no longer wanted
    note        the note to write in an ordinary .claude/skills
    configure   an agent's file to write or remove for a server

and findings, which the tool reports and does not act on:

    config-refused  a configuration file it refuses: nothing is planned
                    in that repository or beneath it
    off-branch      a child whose working tree is on a branch other
                    than the declared one: nothing is planned in it or
                    beneath it
    path-taken      a path taken by something that is not a
                    repository, or that is or passes through a
                    symbolic link; and a child with no remote whose
                    path is a repository, or is not a directory
    other-remote    a path taken by a repository cloned from another
                    remote
    undeclared      a repository beneath this one, or a directory with
                    a configuration, that no entry declares or whose
                    entry is gone. A git submodule, which its
                    repository tracks, is not one. The directories the
                    exclusions in force name (section 1) are not looked
                    in
    missing         a child with no remote whose directory is not there
    name-taken      a path where the tool would make a link, held by
                    something that is not the tool's, or named by
                    more than one skill or command
    name-repeated   a skill with the name of another skill in a
                    directory above it in the same repository; detail
                    is the other's path
    methodology-refused  a methodology with a skill whose name does
                    not begin with the methodology's name and a
                    hyphen: nothing of it is linked
    lock-differs    a node's skills-lock.json that does not hold
                    what its sources declare (section 6)
    lock-undeclared an entry of a node's skills-lock.json that its
                    sources do not declare (section 6)

A plan is a JSON object:

    pos         2
    actions     an array, in an order they can be done in
    findings    an array
    warnings    an array of strings: for each configuration read, the
                node's path and each warning its reader gave, as
                ".: unknown-key: colour". The tool reports them and
                acts on none; they do not make a plan non-empty

An action is an object whose do is the action's name. With it:

    clone       path, branch, and remote or of
    exclude     repository and path, the path relative to the
                repository
    archive-excludes  repository and paths, a sorted array of archive
                directory paths relative to that repository
    install     path, that of the auto/ directory, and version
    link        path and target, the text of the link
    unlink      path
    note        path

A finding is an object with finding, its name, path, and where there
is more to say, detail. Every path is relative to the root of the
tree but an exclude's, and the root itself is ".".

When the tree is as declared, the plan is empty. What is beneath a
child that is not yet cloned cannot be told from the disk, so after the
second step has cloned a child the first is run again, until a plan is
empty.

The tool keeps these rules:

  - A node declares only beneath itself. A path is relative, holds no
    "..", and passes through no symbolic link.
  - A mounted child's configuration is read from its declared branch as
    committed, and not from its working tree, so configuration that is
    not yet merged mounts nothing. The configuration of the repository
    the tool is run in, and of each directory of a repository, is read
    from the working tree.
  - It replaces only its marked archive block and its auto/
    directories, otherwise never writes over what is there, never
    removes a working tree, and never writes outside the tree it is run
    in. In a product it writes nothing, and removes only a link it
    made.
  - Run in a repository, it takes that repository as the root. It does
    not look for a container, and a link whose target is outside the
    tree is left as it is.
  - It keeps no record of the links it made: what section 6 says of a
    link's target is how it knows its own.

The archives ROOT command applies only archive-excludes actions from
a fresh plan and prints the remaining plan. It clones nothing, installs
nothing and changes no link. Initiation and tree-building commands use
this operation after writing configuration.

The install ROOT SOURCE command applies only the exclude, install,
link, unlink and note actions from a fresh plan made with SOURCE, the
links to each node's methodologies among them, and prints the
remaining plan. It clones nothing and changes no archive
rule, so it uses no network. A command run in a tree uses this
operation first, so that what is installed there is the source's.

Like plan and apply, each exits 0 for an empty remaining plan, 1 for
remaining work or findings, and 2 for a refusal.


8. Tests

An implementation is tested in real repositories. A test makes a
temporary directory, makes new repositories inside it with git init,
configures them, and tests the tool's behaviour in them.

fixtures/pos-directory/ holds configuration files for both libraries.
Each fixture is a JSON object: about, what it shows; yaml, the file's
text; and either config, what a reader makes of it, or refused, the
kind of refusal. config has projects, image and bin, each a string or
null; methodologies, a string, an array of sources or null, each source
an object of source, ref, skills, an array of strings or null, kind,
and name, the source's name for a methodology and null for a skills
repository; harnesses and exclude, each an array of strings or null;
children, worktrees and archives, each an
array with every default filled in, a child with no remote having null
for its remote and branch, and an archive carrying sweep and path only
when written; server, an object or null; and warnings, an array of
strings, empty when the reader gives no warning.

fixtures/pos-methodology/ holds declarations, as doc/pos-methodology.txt
section 5 describes them.

The tests of the tool in real repositories include a project that
declares a mounted methodology and a local one, each holding a skill
and a command; a methodology with a skill named without its prefix; a
methodology whose entry is removed; one repository mounted as a
product in one place and a methodology in another; a responsibility
that declares methodologies; a skill with the name of another in a
directory above it; and a repository holding a tracked skill of one
slot's name and an untracked command of another's, planned with a
source that supplies both, which has links for the rest and no
finding; and nodes whose skills-lock.json holds what their sources
declare, a source not installed, a skill not installed, an entry of
another ref, an entry of an undeclared source and one of a skill its
source's entry does not name, a GitHub source written as a URL and in
the lock file's shorter form, a skills-lock.json that is not a lock
file, and one in a node that declares no sources.
