The configuration directory
Version 2

A personal operating system is a tree of responsibilities: a root, and
beneath it responsibilities, each of which may hold more, with projects
and products as its leaves. Each is a node. A node is a directory of
the repository that holds it, or a repository of its own, shared with
other people and checked out in place within the tree. This document
says how a node declares what is beneath it and what it needs
configured, in a configuration directory at its root, and what a tool
does with those declarations.

It names no server. poslib and pyposlib read the configuration, and a
server a node names is whichever its owners run. Everything here but
section 5 works with no server at all.

Version 1 of this document is not read: a file that says pos: 1 is
refused, and is rewritten to this version.


1. The file

A node's configuration directory is named .clanka or .pos. The two
names mean the same; .clanka is the one a tool writes. In it the
configuration is config.yaml or config.yml, which mean the same too.
It is committed with the node. A node has one configuration: two
directories, or two files in one, are refused (two-configurations). A
directory without one declares nothing, and what kind of thing it is
follows from that (section 2).

The file is YAML: mappings, sequences and scalars. It uses no anchors,
aliases, tags or second document, and a mapping holds a key once; what
a reader makes of a key written twice is not defined.

A reader takes every scalar as the text written and guesses no type
from it, quoted or not. YAML libraries differ over what a bare word
is, and one that resolves types may resolve a quoted word too. The
keys below say what each value is:

    a string    any text but the empty one, null and ~
    a boolean   true or false, in those letters
    an integer  a whole number in digits, with no leading zero

So a branch named 1.10 or no is that text, and a value left empty is
refused.

The top level is a mapping:

    pos             2, the version of this document; required
    projects        where this node's projects belong: a path beneath
                    it, usually projects/. It makes the node a
                    responsibility
    methodologies   where this node's methodologies belong: a path
                    beneath it, usually methodologies/. It makes the
                    node a project
    image           the container image this node's commands run in
    exclude         the directories a walk of this node does not enter
                    (below)
    children    what is declared beneath this one (section 2)
    worktrees   other working trees (section 3)
    archives    where archives are kept (section 4)
    server      the server this repository is bound to (section 5)

A node is a responsibility or a project, and says which by the one of
projects and methodologies it has. A responsibility holds projects and
has no methodologies; a project has methodologies and holds no
projects. A file with both is refused (bad-value). A file with neither
is not refused: its node is unconfigured, which a tool reports, and a
person is asked which it is before the node is used.

A final slash on either path is dropped.

image is written on a line of its own, as "image: NAME" from the start
of the line, with NAME unquoted and holding no space, quotation mark
or #, so that a tool with no YAML reader finds it by its line. Any
other way of writing it is refused (bad-value).

exclude is a sequence of strings. Each is the name of a directory, or
a glob over one with * for any text, which keeps a walk out of every
directory of that name beneath this node, however deep; or, when it
holds a slash, a path beneath this node, which keeps a walk out of
that directory and what lies beneath it. A final slash is dropped. The
exclusions in force at a directory are those of the nearest node at or
above it that has the key, replacing what it would inherit; when no
node has it, they are

    archives, attic, node_modules, "_*", ".*"

that is, archives and attics, Node's modules, and every name beginning
with an underscore or a dot. An empty sequence excludes nothing. A
glob beginning with * is quoted, as YAML asks. What exclude governs is
reading: a tool that walks a node for its files, its undeclared
repositories or its archive scopes does not enter an excluded
directory. A directory named archives is an archive scope wherever it
lies, whether or not the walk enters it.

A reader reads the keys written here. A key it does not know, at any
level, is a warning, which names the key by its place in the file, as
"unknown-key: children[0].pin"; the key is left unread and the rest of
the file is read. So a file written for a newer version of this
document is read by an older reader with the newer key's default,
which is always what the older reader did. The version number changes
only when a key's meaning changes.

A reader refuses the whole file for a version it does not know, and
for a value it cannot read. A refusal has a kind:

    not-yaml          the text is not readable as YAML
    not-a-mapping     the file, or an entry, is not a mapping
    unknown-version   pos is a number other than 2
    missing-key       a required key is absent
    wrong-type        a value is not of its key's type
    bad-path          a path this document does not allow
    bad-value         a value this document does not allow
    two-configurations  the node has more than one configuration

The file holds no credential. What a person signs in with is theirs and
stays out of a repository other people share.


2. Children

children is a sequence. Each entry is a mapping:

    path        where the child is, relative to this node
    remote      the git remote it is cloned from; absent for a child
                that is a directory of this node's repository
    branch      with remote, the branch its working tree rests on;
                master when absent
    skills-up   with remote, true if the child's skills are also linked
                into this repository (section 6); false when absent

An entry is a boundary. Its path and everything beneath it is the
child's and not this node's. The entry does not say what the child is;
what is at the path does:

    a configuration that says where its methodologies belong   a project
    any other configuration                             a responsibility
    no configuration                                           a product

A responsibility is a branch of the tree: it declares children of its
own, each node naming only what is directly beneath it. A project and a
product are leaves. A product is a subject, under its own rules, and
this document says nothing of what is in it.

path is any path that stays beneath the node: relative, with no empty
part and no part that is . or .., and no backslash. No folder name
carries meaning. It does not pass through another child: what is
beneath a child is the child's to declare.

A child with a remote is a repository checked out in place. branch is
the branch the work is based on. That is usually the repository's
default branch. For the length of a feature branch that takes many pull
requests it is that branch, and the entry is changed back afterwards.

The repository that holds the declaring node does not track such a
child. Its path is written to that repository's .git/info/exclude
before the child is cloned, since staging everything in a container
records an unexcluded child as an embedded repository. The line written
for a path is the path from the repository's root with a slash before
it, which anchors it there.

A child with no remote is a directory of the same repository, tracked
and committed with it. It has no branch and no skills-up, and an entry
that gives it either is refused (bad-value). Nothing is excluded or
cloned for it. What its own configuration declares is declared for the
repository it is part of.

A responsibility's one-file projects are Org files where its projects
belong, and no entry declares them: making the file is the commitment.
A project that needs a directory is given one, with a configuration,
and is then declared.


3. Worktrees

worktrees is a sequence of working trees that are not scopes: a
repository that does not follow this layout, or a branch other than the
one a child rests on. Each entry is a mapping:

    path        where it is checked out, relative to this node:
                PATH/_worktrees/NAME, or _worktrees/NAME, where PATH
                is beneath the node and not in a child
    of          the path of one of this node's children that has a
                remote: the working tree is a git worktree of that
                child's clone
    remote      in place of of: the git remote it is cloned from, a
                clone of its own
    branch      the branch it rests on; required with of, master when
                absent with remote

A working tree beneath _worktrees is disposable once its commits are
pushed. Its path is written to .git/info/exclude as a child's is. The
commits of a git worktree are in its child's clone, so it is that clone
whose unpushed branches matter.


4. Archives

archives is a sequence saying where an archive is kept. An archive
belongs to a scope: the directory that holds it. Each entry is a
mapping:

    scope       the scope's path beneath this node, not in a child;
                "." is the node itself
    kept        committed: on disk and committed with the repository
                uncommitted: on disk and not committed, its path
                ignored by Git
                remote: by a keeper (doc/remote-archive-protocol.txt)
    url         with remote, the base URL the keeper gives the scope's
                ledger
    ledger      the id of the scope's ledger, a UUID in canonical form
                with lower-case letters; optional, with any kept

A scope no entry names keeps its archive uncommitted. In every case the
ledger stays with the scope and is committed.

The entry for an archive is looked for in the nearest node at or above
its scope: the nearest directory with a configuration.

The tree tool maintains a marked block in each repository's
.git/info/exclude for its uncommitted archives. It covers each declared
node, each explicitly named archive scope (even before its directory
exists), and other scopes found by their archives directories. It
does not enter the directories the node's exclusions name (section 1),
undeclared nodes, or products. A declared child reads its own policy;
a parent's default does not override it.

Patterns are anchored at the repository root, match directories only,
and quote spaces and Git glob characters. When a policy changes, the
block is replaced, leaving all rules outside it alone. Committed and
remote archives get no exclusion from this block. A damaged block,
symbolic link at an archive path or exclude file, or a refused local
node configuration is reported and leaves the repository's block
unchanged. The tool does not remove files from Git's index; already
tracked files stay tracked. Existing user ignore rules, including
/archives/ written by earlier initiate versions, stay as they are.

A ledger otherwise draws its id when its first event is made. A keeper
may be bound to a ledger's id before that event exists, so an entry can
say what the id is. An entry whose ledger is not such a UUID is refused
as bad-value, and so is a file in which two entries name one ledger.


5. The server

server binds a repository to a server its owners run. It is read from
the configuration at a repository's root. It is a
mapping:

    name        what a coding agent knows the server by
    mcp         the URL of the server's MCP endpoint

Absent, the repository is bound to none.

A binding reaches down and never up. The server is configured for
sessions started in this repository and in the repositories beneath it,
and for none above it: what a shared repository declares cannot reach
the repository that contains it.

For each coding agent a tool supports, it writes the file that agent
reads for MCP servers, in this repository and in each repository
beneath it. The files are untracked, with their paths in
.git/info/exclude, and a file a repository tracks is left as it is.
Nothing is written outside the tree.


6. Skills

ClankOS shares skills from .agents/skills/, one directory each, holding
a SKILL.md. Repositories may keep other skill layouts. Existing files,
directories and links at .claude/skills are left alone, without a
finding or a migration. Discovering and evaluating skills in other
locations is separate from bringing the tree to its declarations.

If .agents or .agents/skills is a file or symbolic link, that
repository's skill layout is left alone: no skills are read from it or
linked into it. An ordinary .agents/skills directory can contain other
files; they keep their names and are not shared as skills. Processing
continues in the repositories beneath it.

A coding agent looks for skills from where a session starts up to the
root of that repository and no further. A repository mounted in place
therefore sees none of its containers' skills. Links supply them:

  - Down, always. Each of a repository's own skills is linked into
    .agents/skills/ of every repository beneath it, at any depth.
  - Up, only when asked. Where a child's entry has skills-up true, the
    child's own skills are linked into this repository, and no farther.
  - Only a repository's own skills are linked. A link is never linked
    on, so nothing returns to where it came from and nothing passes
    from one child to another.
  - Where two skills have one name, the nearer has it: a repository's
    own skill before any link, a nearer container's before a farther
    one's, and a container's before a child's. Two children's skills
    of one name are a finding, and neither is linked.
  - A link is a relative symbolic link to the skill's directory. It is
    untracked, with its path in .git/info/exclude of the repository it
    is made in.
  - Where a repository has skills and no .claude/skills, a link to
    ../.agents/skills is made the same way, untracked and excluded,
    provided .claude is absent or an ordinary directory. An existing
    .claude file or symbolic link is left alone too.

A linked skill calls only what travels with it or is installed: scripts
within its own directory, which the link carries, and installed
commands. Nothing in a repository's bin/ is linked. A skill that calls
into its own repository outside its directory holds a file named
.pos-local in its directory, and is not linked.


7. The two steps

One tool brings a tree to what its configurations declare, in two
steps.

The first step prints a plan: what needs to be done, if anything. It
changes nothing and uses no network. Everything in a plan can be told
from the disk.

The second step is given a plan and does those things and nothing else.
It makes the plan afresh first and refuses, as stale-plan and having
done nothing, a plan the tree no longer gives. If an action cannot be
done it stops and refuses, as failed, and what it did before stays
done. It prints the plan that remains.

A plan holds actions:

    clone       a declared child or worktree that is not there
    exclude     a path to add to a .git/info/exclude
    archive-excludes  replace the managed archive block in info/exclude
    link        a skill link to make, or the .claude/skills link
    unlink      a link the tool made whose skill or declaration is gone
    configure   an agent's file to write or remove for a server

and findings, which the tool reports and does not act on:

    config-refused  a configuration file it refuses: nothing is planned
                    in that repository or beneath it
    off-branch      a child whose working tree is on a branch other
                    than the declared one: nothing is planned in it or
                    beneath it, and links to its skills are left
    path-taken      a path taken by something that is not a
                    repository, or that is or passes through a
                    symbolic link; and a child with no remote whose
                    path is a repository, or is not a directory
    other-remote    a path taken by a repository cloned from another
                    remote
    undeclared      a repository beneath this one, or a directory with
                    a configuration, that no entry declares or whose
                    entry is gone. A git submodule, which its
                    repository tracks, is not one. The directories the
                    exclusions in force name (section 1) are not looked
                    in
    missing         a child with no remote whose directory is not there
    unconfigured    a node whose configuration says neither where its
                    projects belong nor its methodologies. What it
                    declares is planned all the same
    name-clash      two children's skills of one name

A plan is a JSON object:

    pos         2
    actions     an array, in an order they can be done in
    findings    an array
    warnings    an array of strings: for each configuration read, the
                node's path and each warning its reader gave, as
                ".: unknown-key: colour". The tool reports them and
                acts on none; they do not make a plan non-empty

An action is an object whose do is the action's name. With it:

    clone       path, branch, and remote or of
    exclude     repository and path, the path relative to the
                repository
    archive-excludes  repository and paths, a sorted array of archive
                directory paths relative to that repository
    link        path and target, the text of the link
    unlink      path

A finding is an object with finding, its name, path, and where there
is more to say, detail. Every path is relative to the root of the
tree but an exclude's, and the root itself is ".".

When the tree is as declared, the plan is empty. What is beneath a
child that is not yet cloned cannot be told from the disk, so after the
second step has cloned a child the first is run again, until a plan is
empty.

The tool keeps these rules:

  - A node declares only beneath itself. A path is relative, holds no
    "..", and passes through no symbolic link.
  - A mounted child's configuration is read from its declared branch as
    committed, and not from its working tree, so configuration that is
    not yet merged mounts nothing. The configuration of the repository
    the tool is run in, and of each directory of a repository, is read
    from the working tree.
  - It replaces only its marked archive block, otherwise never writes
    over what is there, never removes a working tree, and never writes
    outside the tree it is run in.
  - Run in a repository, it takes that repository as the root. It does
    not look for a container, and a link whose target is outside the
    tree is left as it is.
  - A link is the tool's if it is an untracked symbolic link in
    .agents/skills/ whose target is a skill's directory in another
    repository of the tree. It keeps no record besides.

The archives ROOT command applies only archive-excludes actions from
a fresh plan and prints the remaining plan. It clones nothing and
changes no skill link. Initiation and tree-building commands use this
operation after writing configuration. Like plan and apply, it exits
0 for an empty remaining plan, 1 for remaining work or findings, and
2 for a refusal.


8. Tests

An implementation is tested in real repositories. A test makes a
temporary directory, makes new repositories inside it with git init,
configures them, and tests the tool's behaviour in them.

fixtures/pos-directory/ holds configuration files for both libraries.
Each fixture is a JSON object: about, what it shows; yaml, the file's
text; and either config, what a reader makes of it, or refused, the
kind of refusal. config has kind, which is responsibility, project or null;
projects, methodologies and image, each a string or null; exclude, an
array of strings or null; children, worktrees and archives, each an
array with every default filled in, a child with no remote having null
for its remote and branch; server, an object or null; and warnings, an
array of strings, empty when the file holds no key the reader does not
know.
