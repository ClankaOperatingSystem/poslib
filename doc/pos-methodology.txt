The methodology directory
Version 1

A node, a project or a responsibility, uses methodologies: each a
repository or a directory declared directly beneath the node's
methodologies path (doc/pos-directory.txt, section 2). A methodology
supplies skills and commands, which section 6 of that document says
how the tree tool links into the node. This document says what else a
methodology holds: a declaration of the kinds of canon its commands
create and maintain in the node; the checks its skills supply for
them; and what a tool does with both. Below, "the project"
is the node that declares the methodology, whichever of the two it is.
A source a node declares under methodologies as a sequence is
installed in the node instead (pos-directory, section 6), and no
declaration of it is read.

A methodology has no configuration. It declares no children and names
no locations; it is what its declaring entry says it is. What it holds:

    version              one line, which names what the directory holds
    skills/NAME/         a skill, named with the methodology's name and
                         a hyphen (pos-directory, section 6), with its
                         checks in scripts/ (section 3)
    bin/NAME             a command
    methodology.yaml     the declaration (section 1); optional

Everything here works with no server and no network.


1. The declaration

methodology.yaml at the methodology's root is YAML, read under the
rules of the configuration (pos-directory, section 1): no anchors,
aliases, tags or second document; every scalar is the text written; a
key the reader does not know is a warning, named by its place, and the
rest is read; a value the reader cannot read refuses the whole file,
with a kind of refusal from that document's list; the version number
changes only when a key's meaning changes.

The top level is a mapping:

    methodology    1, the version of this document; required
    canon          the kinds of canon this methodology maintains in a
                   project (section 2); absent means none
    checks         commands of its bin/, which the lint does not run
                   and reports (section 3); absent means none

A methodology whose directory has no methodology.yaml declares no
kinds: it supplies skills, with their checks, and commands only. A file that
is empty lacks its version (missing-key); one that is not a mapping is
refused (not-a-mapping).


2. Kinds of canon

canon is a sequence. Each entry is a mapping:

    kind        the kind's name, a string; one entry per name, a name
                written twice refused (bad-value)
    at          where the kind's instances are in a project that uses
                the methodology: a path beneath the project. With a
                final slash, a directory holding one file per
                instance; without, the one file that is the instance.
                Or a URL, for a kind kept outside the repository: a
                database behind an API, say
    format      a word naming what the instances are written in, for a
                reader: markdown, json, org, or any other word. It
                binds nothing: no tool reads an instance because of
                it, and no format is required; absent, none is named
    derived     true for a kind the methodology's commands rebuild
                from other kinds and a person does not edit; false
                when absent
    entrance    where a reader starts to find the instances, a path
                beneath the project or a URL; when absent, at

A path in at or entrance is as a child's path is (pos-directory,
section 2): relative, no empty part, no part that is . or .., no
backslash (bad-path otherwise). It is a path in the project, not in
the methodology: the methodology supplies the kind and the means, and
the project owns the instances. A kind whose at is a directory may be
empty in a project that has recorded nothing yet. A URL begins with a
scheme and ://, and is taken as written: nothing of it is checked, and
no tool reads it. A method whose canon is a database behind an API
declares the kind at the API's URL, so that a reader is told where it
is; what the method keeps in the repository beside it, a journal of
its work, say, is a kind of its own with a path.

A methodology's own files are not canon of any project. A tool that
walks a project for its files does not enter a methodology, whether it
is a directory of the project's repository or a repository mounted
there (pos-directory, section 2), so a methodology's documentation is
never a project's tasks.

What a tool does with a kind: nothing to the instances. The corpus
reads Org files and no instance of a kind because of its format; an
instance that happens to be an Org file in the project is read as any
Org file of the project is. What the declaration gives a tool is the
knowledge that the kind is there and where a reader starts, which the
start-up report prints (section 4).


3. Checks

A check is a script in a skill: skills/NAME/scripts/check-CHECK, an
executable file, with whatever it needs beside it in the skill, such as
scripts/lib/. The lint runs every check of every skill of each
methodology a project declares, after its own checks of the project's
Org files, in the order of the skills' names and then the checks':

  - for a methodology mounted beneath the methodologies path, the
    skills in its skills/;
  - for a source declared under methodologies as a sequence, the skills
    installed from it, each a directory in the project's
    .agents/skills/ with an entry of that source in its
    skills-lock.json (pos-directory, section 6).

A check

  - is run with the project's directory as its working directory and no
    arguments;
  - prints findings, one per line, as FILE:LINE: MESSAGE, FILE relative
    to the project; a line not of that form is a finding at the project
    itself, with the line as its message;
  - exits 0 for no finding, 1 for findings, and 2 when it could not
    check; the lint reports the last as a finding at the skill's
    directory, with what the check printed on standard error.

The lint prints a check's findings among its own, FILE relative to the
root, sorted with them. A check reads what it likes within the project
and writes nothing; a check that writes is a defect of the methodology.

checks in a declaration names commands in the methodology's bin/, the
form a check had before checks were scripts of skills. The lint runs
none of them: it reports a declaration that has checks as a finding at
the methodology's path, naming them, so that each can be moved into a
skill's scripts/. A declaration the lint cannot read is a finding there
too. A check named with a slash is refused (bad-value).


4. What a reader is told

The start-up report (pos-startup; clankos' docs/startup-prompt.txt)
reads the corpus, every Org file the tree's configurations allow, and
nothing else. After "Files read" it prints, for each project of the
tree that uses a methodology declaring kinds, one line per kind:

    Canon of other kinds, not read:
      PROJECT  METHODOLOGY  KIND  AT  start at ENTRANCE

PROJECT is the project's path as the report labels its scopes, "." for
the root; the others are the declaration's, with at and entrance
relative to the project. A methodology whose declaration is refused is
one line, naming the methodology and the refusal, so that a reader
knows a kind may be missing from the list. The section is absent when
no methodology of the tree declares a kind.

The report's views stay what they are: items of the corpus's Org
files. An instance of another kind is in no view.


5. Tests

fixtures/pos-methodology/ holds declarations for both libraries, as
fixtures/pos-directory/ holds configurations (pos-directory, section
8). Each fixture is a JSON object: about; yaml, the file's text; and
either declaration, what a reader makes of it, or refused, the kind of
refusal. declaration has methodology, the version; canon, an array of
kinds with every default filled in, format a string or null, derived
true or false and entrance as written or as at; checks, an array of
strings; and warnings, an array of strings.

The tests of the tools in real repositories include a project with a
methodology whose Org file is not read as the project's, local and
mounted; a report that lists a declared kind with its entrance; and a
lint that runs the checks of a mounted methodology's skills and of a
skill installed from a source, and reports their findings among its
own; and a lint that reports a declaration that names checks.
